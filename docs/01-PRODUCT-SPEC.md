# 01 — Product specification

## 1. One sentence

RomMMobile is an Android client for a self-hosted **RomM** server that lets you browse the library with the same visual language as the web app and **download ROMs straight into the right folder of the frontend installed on the device**, using the handheld's physical controls.

## 2. Goals

1. **Zero questions about the path.** After onboarding the user must never again answer "where do I save this file?". Select the game, press download, and the file lands where the frontend will find it.
2. **Gamepad-first.** Everything is reachable with D-pad/stick/buttons. Touch stays fully functional but is never required.
3. **RomM style.** The interface takes the palette, hierarchy and components of the RomM web app, corrected where the web app does not adapt well (square screens, short screens, TVs).
4. **Truly adaptive.** The same app must be readable on an almost square 1240×1080 screen (Retroid Pocket Classic), on a 1920×1080 landscape screen (Retroid Pocket 5, Odin 2), on a 20:9 portrait phone and on a 720p/1080p TV.

## 3. Non-goals (v1)

- **It does not launch games.** No emulator integration, no launch `Intent`, no embedded cores. This is explicitly out of scope: that role belongs to the user's frontend (ES-DE, Daijishō…).
- No web emulation (EmulatorJS), no streaming.
- No save sync, no RetroAchievements (worth evaluating after v1, see roadmap).
- No scraping of its own: metadata comes from RomM.
- No writing/modifying the library on the server (upload, rename, delete on the server side).

## 4. Target devices

| Class | Examples | Peculiarities the app must handle |
|---|---|---|
| Almost square portrait handheld | Retroid Pocket Classic (3.92", **1240×1080**, ~419 dpi, ~10:9) | very low height in dp (~410 dp), no bottom bar |
| Landscape handheld | Retroid Pocket 5, Odin 2/3, AYN Odin, RG Cube (1:1 720×720), Ayaneo Pocket | wide and short layout, focus at arm's length |
| Phone | any 20:9 | classic layout, bottom bar |
| Android TV / box | Nvidia Shield, Fire TV | **the SAF picker may not exist**, no touch, overscan |

Technical requirements: **minSdk 26** (Android 8), **target/compileSdk 35+**. Distribution via sideload (APK in GitHub Releases), not the Play Store — this allows `MANAGE_EXTERNAL_STORAGE`.

## 5. App structure

Three main sections, like RomM, in a bottom bar (or a side navigation rail, see the UI doc):

1. **Platforms** — grid of cards with the official platform icon and the ROM count. This is the home.
2. **Collections** — user collections, virtual collections (franchise, genre, publisher, mode) and smart collections.
3. **Search** — server-side search across the whole library.

Outside the main navigation: **Downloads** (queue, reachable from a persistent mini bar and from the menu), **Settings**.

## 6. Flows

### 6.1 Onboarding (first run)

Five steps, each navigable with the gamepad only, each with a "Back":

1. **Server** — URL field (`http://192.168.1.10:8080`), automatic normalisation (adds `http://` if missing, strips the trailing slash), background reachability test on `GET /api/heartbeat` with a live status indicator (800 ms debounce). Shows the detected RomM version.
2. **Login** — username/password (`POST /api/login`) or a **QR scan** of the client API token (`rmm_…`) generated by the web app. The QR is the preferred route on handhelds: typing a password with the D-pad is torture. If the device has no camera, the manual field remains.
3. **Launcher** — grid of choices: **ES-DE**, **Daijishō**, **Beacon**, **iiSU**, **Cocoon**, **Pegasus**, **Dig**, **Other/Custom**. One line of description for each. The choice determines the folder preset (doc 05).
4. **Storage permission and ROM folder** — request for `MANAGE_EXTERNAL_STORAGE` (via `ACTION_MANAGE_APP_ALL_FILES_ACCESS_PERMISSION`) with an honest explanation of why; if denied or unavailable, fallback to SAF (`ACTION_OPEN_DOCUMENT_TREE`). Then selection/confirmation of the ROM root folder: the app **proposes** the known paths of the chosen launcher and those found on the device (internal storage + SD), and the user confirms with one button.
5. **Summary and verification** — the app scans the root folder, matches the existing subfolders to the server's platforms (doc 05) and shows a `RomM platform → folder on the device` table with the status: ✅ found, ➕ to create, ✏️ to choose. The user can correct every row. "Finish" is enabled even with unresolved rows (they are resolved at the first download for that platform).

Rule: onboarding can never get stuck. If the SAF picker does not open (Android TV, Fire TV) or the permission is denied, the app explains the problem and offers manual entry of the absolute path.

### 6.2 Browsing and downloading

`Platforms → [SNES] → cover grid → [game] → Download`

- The grid shows the 2D cover taken from the server (no game files are downloaded in advance).
- **Alphabet rail on the right** (`# A B C … Z @`) always visible in portrait, as in the web app: select the letter and the grid jumps to that offset. Fed by the API's `char_index`, not computed locally.
- One button toggles **grid ↔ list** (the list shows name, region, size, status).
- The download starts **without asking anything**: the destination is already decided. A toast says where it went ("→ ROMs/snes").
- If the platform has no folder associated yet, and only in that case, a dialog appears with a ready-made proposal ("Create `ROMs/snes`?") confirmed with one button.

### 6.3 Download management

Persistent mini bar at the bottom (above the nav): current file name, percentage, speed, `n queued`. Selecting it opens the Downloads screen with Active / Waiting / Completed / Failed queues, per-item actions (pause, resume, cancel, retry, open folder) and global actions (pause all, clear completed).

Downloads survive leaving the app: queue persisted in the DB, foreground service with a notification.

## 7. Non-negotiable rules

1. **Never a partial file in the frontend's folder.** The file is downloaded into the app's private cache as `.part`, verified, then moved. An ES-DE scanning halfway through a download must see nothing.
2. **File names: the server's `fs_name` is used, unchanged.** It is already the correct name (No-Intro/Redump); any rename breaks the frontend's scraping.
3. **A game already on the device is not downloaded again.** The check is by exact file name (plus known extracted/compressed variants), never by substring.
4. **No destructive action without explicit confirmation**, and never on files the app did not download.
5. **A malformed game must not bring down the list.** Every item renders defensively, optional fields nullable with defaults.
